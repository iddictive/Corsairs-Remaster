# Nuclear flash receiver pilot

The hidden `sea-fleet-benchmark` scene used eight Manowars at 1280×800 on an Apple M5 Max, with modern and dynamic lighting enabled. Each run used 160 frames; summaries use the last 32. This is an isolated renderer/ship pilot, not player gameplay or a dense nuclear-battle acceptance run.

The candidate was based on `8db8ed8` plus the in-progress `ShipBlastLights` source changes. Its benchmark binary SHA-256 was `d8cb77be23f0ce13a3de47227fef8f9fe15ae17028a4f340cdcb59b8058fc056`. The stock `sea_fleet_fixture.c` was adapted to create `ShipBlastLights` on realize layer 3 at priority 30; the resulting fixture SHA-256 was `9b6d89d48f1436003dc20660f3f3de1986794ce23ea8b52d9b010c3f84b9fa02`. Inputs otherwise followed `tools/run_sea_benchmark.py` and the installed game resource files.

For this pilot only, the early actor accepted `CORSAIRS_VFX_FIXTURE_BLAST=1`: after clearing its sources, it published point source ID `1<<59` at `(0,40,170)`, RGB `(2.4,1.25,0.48)`, range `660`, attenuation `(1,0,4/(660*660))`, and inserted that source into the same actor list. The baseline used the same binary and fixture with the variable absent. This synthetic fixed source tests receiver/slot/shadow integration; it does not exercise missile launch, blast lifetime, the nuclear plume or water.

`baseline/` and `flash/` contain the frame populations and summaries. The flash run is a recovery run: an intervening telemetry run overwrote the earlier CPU log, and an attempted recovery failed because the trace path already existed. The successful recovery used a fresh trace path. A separate 16-frame telemetry run is retained as `flash/telemetry.json`; it reports the synthetic source as shadowed and all eight selected point shadow cubes complete. The uninstrumented baseline/flash runs also report all eight cubes complete.

In this bounded scene, median CPU wall time was 8.79/8.76 ms and GPU execution union was 6.41/6.62 ms (baseline/flash). Both scene-coverage checks passed. Both runs included the new actor, so its idle overhead was not measured. These samples do not establish a general FPS claim, interaction responsiveness, sustained bursts, or installed-game behavior. Original user reports of fire intersecting ships remain unverified here.

## Actual blast-state pilot

The same hidden fleet fixture was rerun with binary SHA-256 `6d0765ecff24cbe29b088b6bb52c1ecbc98cd96252276877f4e20e1ff7df6f44`. In this disposable binary only, the main ship's `Execute` injected a default `NuclearBlast` after `ExecutePhonkOrdnance` on its 128th execute frame when `CORSAIRS_VFX_REAL_BLAST=1`: it called `EnsureCutFragments()`, set `center=GetPos()+CVECTOR(0,0,80)`, `active=true`, `seed=1`, and appended the blast. The default yield radius is 220. No impact damage or wave was injected. The baseline used the same binary without the environment variable. The temporary injection was removed from the source after these runs.

`real-baseline/` and `real-blast/` retain CPU and GPU frame populations and generated summaries, with no per-frame telemetry in either timing run. A separate telemetry run recorded the actual blast source as shadowed; the retained PNG is the final frame of the uninstrumented flash run. Median CPU wall was 9.00/10.05 ms and GPU execution union 8.71/9.25 ms (baseline/blast), measured over frames 128–159 at 1280×800. The samples cover one short-lived default-yield explosion, not repeated detonations or a live player session. The test did not establish hull intersection correctness, save compatibility or installed runtime behavior.

## Rejected soft ignition candidate

`rejected-soft/shader.patch.txt` records the temporary ignition field; `scene.png` is its final fleet frame. The candidate reused the same blast-state injection and fixture, with binary SHA-256 `5b6fbed3eee802f47f0f3e4de86bf8daf803a71ea6d8ee3da7e536d0d132cffc`. Median CPU/GPU times were 9.15/8.79 ms, with fleet coverage passing. Timings are individual diagnostic runs, not evidence of a speedup. The candidate was rejected because the near blast washed out a large region and obscured the sea and ships. Neither the candidate shader nor diagnostic blast injection remains in product source.

## Transient shell light pilot

In the same eight-ship fixture, the early light entity was additionally attached to execute layer 2. A disposable driver sent the explosion-light message at `(0, 8, 200)` once per frame on frames 128–135; it was removed from product source afterwards. Baseline and burst ran the same instrumented binary, with the trigger disabled/enabled. Over frames 128–159, median CPU was 8.40/8.57 ms and GPU was 6.09/6.18 ms. These are short diagnostic samples, not a gameplay performance acceptance; the timing binary put the selected explosion before normal D3D slots, while the final candidate retains normal slot order. A separate 140-frame run with the final slot order records the newest shell light as shadowed in `shell-light/telemetry.json` after explosion sources were prioritized in the bounded sea shadow selection. Other simultaneous shell lights can remain unshadowed. The test sends the message directly and does not exercise ammunition impact or a loaded save.

The final slot order was then timed using a new pair of runs in `shell-light/final/`: median CPU 8.47/8.96 ms, GPU 6.08/8.45 ms (baseline/burst). Both retain eight complete shadow cubes and workload coverage. The 2.36 ms GPU difference in this short pair is material and differs from the earlier pair; the cause and representative battle performance remain unresolved.

To test whether the shadow itself explained that difference, a disposable selector switch excluded explosion IDs from shadow selection while keeping the injected lights. The same binary ran with the switch on/off; `shell-light/shadow-ab/` records median GPU 6.66/6.75 ms and CPU 9.24/9.14 ms (shadow excluded/included). This short pair does not explain the earlier spread or establish gameplay performance. The selector switch and injected driver were removed afterwards.

# Oreshnik: 4 km versus 8 km

This extends the existing isolated single-attacker replay, not the game runtime.
`diagnostic.py` emits per-trial launch and swept-closest-approach measurements for Patriot at 4 and 8 km. Run it from the repository root with Python 3 and the native compiler. `current.csv` retains the 500-seed run. It uses the current source functions and the same assumptions as the parent replay, including a stationary defender, up to two simultaneous interceptors, repeated launches and 25 ms simulation steps. The retained output includes hashes of its source inputs.

The other CSVs are counterfactual runs of the same diagnostic. Change one source function in the script after extraction: set the Patriot observation interval to 25 ms (`fast-tracking.csv`); replace its 80g-dependent turn bound with the previous fixed 3 rad/s bound (`turn-limit-removed.csv`); set its angular measurement error radius to zero (`no-measurement-noise.csv`); skip targets while observed vertical speed is positive (`descending-only.csv`); remove the Oreshnik fallback launch when the forecast finds no solution (`no-fallback.csv`); or change the guidance acceleration-observation clamp from 250 to 900 m/s² (`acceleration-cap-900.csv`). These are comparisons, not proposed game changes. Results include the source's random launch/fuse/detection variations.

`trajectory-probe.cpp` measures two representative trajectories (trial 27 at 4 km, trial 128 at 8 km) and samples lateral acceleration by differencing velocity over 80 ms. Compile with `xcrun clang++ -std=c++20 -O2 -I experiments/native-metal/engine/src/libs/ship/src -I experiments/native-metal/engine/src/libs/math/include docs/evidence/airdefense-forecast-20261114/oreshnik-4-vs-8/trajectory-probe.cpp -o /tmp/oreshnik-trajectory-probe && /tmp/oreshnik-trajectory-probe`. This is a numerical measurement of the game path, not a claim about a real weapon.

`cadence-*.csv` compares random per-interceptor observation intervals of 25–50, 25–100, 50–100, 50–150 and 80–150 ms, changing only the interval in `initializePatriot` and retaining 25 ms simulation steps. `frequent-delayed.csv` instead samples every 25 ms but observes the target's state delayed by the same random 50–250 ms interval, and linearly extrapolates that delayed state and the measured acceleration. The latter is a single exploratory implementation, not a general result for all delayed trackers. Both retain the 80g turn bound, fuse settings, and all other parent assumptions; neither was integrated into the game.

`lead-95.csv` changes only the computed Patriot lead time by multiplying `distance / max(400, speed + closing)` by 0.95 before the existing 0–2 s clamp. It uses the same measured target data and does not read future trajectory. `lead-95-all.csv` repeats this counterfactual for all four missile types and distances using the parent runner. `seed-873-current.csv` and `seed-873-lead-95.csv` repeat the Oreshnik comparison using a disjoint seed range from the original seed-19 run. Reproduce by applying that substitution to extracted `advancePatriot` in a temporary copy of `diagnostic.py` or the parent runner, and replace `SEED 19u` with `SEED 873u` for the disjoint run. The 0.95 factor is a tuning candidate, not an established physical model or an integrated change.

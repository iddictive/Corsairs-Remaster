# Air-defense forecast and 80g prototype

The subsequent Oreshnik 4 km versus 8 km investigation and its per-trial evidence are in [oreshnik-4-vs-8](oreshnik-4-vs-8/README.md).

`results.txt` records the output of `python3 docs/evidence/airdefense-forecast-20261114/replay.py` on the source hashes printed at its beginning. The runner extracts the current native guidance and interception functions; it constructs the proposed 80g Patriot and Kinzhal trajectory in scratch space. Neither prototype is present in the game runtime solely by virtue of this evidence.

The four distances are attacker launch-to-ship distances, not detection ranges. Each cell uses 500 seeded single-missile attacks against a stationary defender, 8 km detection, a 0.25 s launch interval, at most two interceptors assigned simultaneously, repeated launches, a 25 ms step, and aim points randomized within an 80 m square. It models the full-fire path without islands; it is not a replay of the whole game or a measurement of real weapons. `interceptors` is the total for the cell, not a per-attack cap.

The Kinzhal prototype re-times its original geometric path with a curvature-based speed profile, preserves its endpoint, and adds a bounded returning evasion when there is sufficient time. It uses 55g for nominal curvature and a sampled 65g evasion budget as safety margins toward an 80g total. Its moving-target guidance and manual control have not passed an end-to-end 80g check, so the resulting Kinzhal percentages are exploratory. The Patriot 80g limit is also injected only in this replay. Test matrices do not prove visual behavior, frame rate or installation.

The copied `player-simulation.cpp` is the task's isolated simulation input; the small local `matrix.py` provides source-function extraction. The runner prints SHA-256 hashes of those inputs and the native source, compiles with `xcrun clang++ -std=c++20 -O2`, and fails if an input changes during execution. It requires the user's existing Codex temporary-directory cleanup helper.

`storm-20-matrix.txt` repeats the runner after changing the Storm profile speed from 800 to 640 and the trajectory speed bound from 1400 to 1120; other conditions are unchanged. `storm-forecast-half-second.txt` repeats that run with only the extracted `estimatePantsir` function's bounded acceleration horizon changed from 3 s to 0.5 s. This second run is a diagnostic counterfactual, not the game's implementation: it raises the 1 km Storm interception result but also changes Kinzhal results substantially, so it does not establish an acceptable fix. Reproduce it by applying that single substitution in a scratch copy of `replay.py`, preserving its project-relative input paths. Kinzhal's 80g timing and evasion remain simulation-only in both runs.

`current-runtime-replay.py` extracts the current source's flight, prediction, motor, evasion and fuse functions. Its results and exact input hashes are in `current-runtime-results.txt`; run it with Python 3 and the same local compiler prerequisites. It is still an isolated static-defender approximation: it omits terrain, moving ships, volleys and parts of the game scheduling. It uses the source's Kinzhal timing and 80g Patriot turn limit. Results cannot establish live-game behaviour, frame rate, or installed state. `before-kinzhal-80g.txt` preserves the preceding run without Kinzhal timing; `before-patriot-kalibr-tuning.txt` preserves the run before the subsequent guidance and evasion adjustments.

`before-observed-forecast.txt` compares the same driver and current missile profiles against `phonk_ordnance.cpp` from commit `d2b825d`, with the same source-level 80g Patriot turn limit applied. It removes the new forecast helper calls and horizon arguments from the driver. This comparison keeps the existing game Kinzhal flight model in both cases. Recreate the baseline by extracting that file with `git show d2b825d:experiments/native-metal/engine/src/libs/ship/src/phonk_ordnance.cpp`, applying the Patriot turn limit shown in the current source, and using the old forecast call signatures. The comparison showed a substantial change to Kinzhal/Pantsir at 8 km and did not resolve the close-range Storm result; the current change remains unaccepted for delivery. A parallel whole-run timing (including four compilations and all trials) was 8.65 s before and 8.78 s after; this is not an in-game FPS measurement.

The `kinzhal-diagnostic-*.txt` files add trial-level launch and swept-distance counters or change one Patriot parameter in the same 500-seed harness. `old-turn` replaces the current 80g-dependent turn limit with the previous 3 rad/s limit; `fast-track` changes observation cadence to 1 ms; `fast-fuse` lowers sensor enable speed from 350 to 80 m/s. These are counterfactuals, not production recommendations. The acceleration probe samples 100 stationary-target Kinzhal trajectories with the same launch seeds, comparing velocity directions at 30 ms intervals; it excludes evasion, moving targets, and the first and last 35 ms. Compile with `xcrun clang++ -std=c++20 -O2 -I experiments/native-metal/engine/src/libs/ship/src -I experiments/native-metal/engine/src/libs/math/include docs/evidence/airdefense-forecast-20261114/kinzhal-acceleration-probe.cpp -o /tmp/kinzhal-acceleration-probe && /tmp/kinzhal-acceleration-probe`. Its sampled lateral acceleration is a gameplay-trajectory measurement, not a real-weapon performance claim.

`kinzhal-acceleration-location.cpp` and its results use an 80 ms velocity-difference window, identify the location of the highest sampled lateral acceleration for each of the same 100 stationary-target trajectories, and exclude evasion and the first and last 60 ms. Compile with the same command above, substituting that filename. The `no-bend` counterfactual sets `m.shotId=0` after `varyMissile` (retaining the same random flight variation) to remove shot-specific lateral offsets; `arc0` instead sets `m.flightVariation.arcPattern=0` after `varyMissile`. These are diagnostic substitutions, not source changes.

`kalibr-evasion-{5,10,20}g.txt` records counterfactual runs using the same current runner with only the header constant `kalibrEvasionAcceleration` changed to the indicated value; `current-runtime-results.txt` contains 30g. The limit concerns the additional smooth evasive displacement, not total missile acceleration. `kalibr-evasion-acceleration-probe.cpp` isolates that contribution with 1,000 samples; its maximum sampled value was 25.72g for the 30g limit. It can be compiled with the same include paths as the other probes. `kinzhal-kalibr-dynamic-check.txt` records 25 ms whole-trajectory acceleration samples with interceptions: Kinzhal's maximum was 78.8g, while Kalibr's was 71.7g including its existing base trajectory. A no-defense run sampled 64.1g on Kalibr's existing 1 km flight, so the total is not claimed to be 30g. Both missile evasion offsets are prescribed smooth curves, not fully integrated free-flight physics.

`evasion-inertial-25ms.txt` and `evasion-inertial-12_5ms.txt` record the later state-integrated evasion candidate with current direct-contact radii, 500 seeds per cell and the same static-defender assumptions described above. The 12.5 ms result is generated by executing the same `current-runtime-replay.py` with `#define DT .025f` replaced by `#define DT .0125f`; input hashes are printed in each output. The difference is substantial in some cells (notably Pantsir versus Storm at 1 km), so neither matrix establishes stable game probabilities. `evasion-inertial-probe.cpp` is a task-local sampled fixed-target geometry probe, not the game update loop or a moving-target guarantee. The candidate was not checked in the installed game; frame time and real visual quality remain unmeasured.

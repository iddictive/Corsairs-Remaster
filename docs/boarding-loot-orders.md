# Boarding loot orders

## Owner and contract

Both supported `src/gameplay/variants/mainhero/` dialogues expose the loot order
in ordinary `TalkSelf_Main`. Delivery preserves the receipt's selected variant;
adding this control must not replace the rest of that variant's dialogue.

`Boarding_CabinLootMode`, `Boarding_SetCabinLootMode` and the cabin event handler
are generated by `tools/gameplay/fleet-gameplay.json` into `Loc_ai/LAi_boarding.c`.
The mode belongs to `pchar.BoardingLootMode` and survives the normal save codec:

| Value | Cleared enemy cabin behavior |
| --- | --- |
| Missing, invalid or 0 | Existing sailor conversation offers collection or manual inspection. |
| 1 | Existing collection/capture path runs without creating a sailor conversation. |
| 2 | No sailor and no automatic collection; ordinary manual inspection/exit remains. |

Switching in a cleared cabin removes the temporary speaker, restores the ordinary
exit handler, clears the previous offer and schedules the selected policy after
the thoughts dialogue closes. Outside the current cabin, changing the order only
stores the preference. Finished cabins and fort boarding keep their existing path.
Collection, exact item/cash conservation and protected-item preservation on manual
departure remain owned by `docs/fleet-gameplay-audit.md`.

## Evidence and acceptance

The played receipt selected `standard.c`, which lacked the menu. Independently,
the installed cabin handler ignored `BoardingLootMode`; merely restoring a menu
would not restore silent/manual behavior. An actual-script VM fixture reproduces
the ignored modes before the repair, then checks default/silent/manual dispatch,
mid-cabin speaker release, repeated completion, wrong-cabin rejection, invalid
values and four save-codec rounds. Entity/dialogue/finish dispatch and the delayed
event are explicit adapters in that focused fixture.

The complete played PROGRAM with the candidate boarding/traffic consumers and
actual public/private shared headers compiles with no script errors. Its real
MainHero wrapper exposes the ordinary order link, cancellation link and all three
selection branches; only native dialogue closing is adapted there. These checks
accept source behavior. Installed dialogue, actual chest transfer and scene
transition still require player replay, recorded separately in `docs/runtime.md`.
